Core thesis过去一年客户实践总结

最成功的 agent 实现，通常不是最复杂的实现

简单优先

先用最简单的方案解决问题，只有当收益明确时才增加复杂度。

组合模式

有效系统更多依赖清晰、可组合的 workflow 和 agent 模式。

可调试性

框架能加速起步，但也可能遮蔽 prompt、response 和真实控制路径。

DefinitionsAnthropic 的关键区分

Workflows 与 Agents 都属于 agentic systems，但控制权不同

Workflows

LLM 和工具通过预定义代码路径编排，适合可拆解、可预测、需要一致性的任务。

Agents

LLM 动态决定流程和工具使用方式，适合开放式、步骤数难以预判的问题。

Decision gate何时使用 agentic systems

复杂度应该由任务收益证明，而不是由技术热度驱动

1st 先优化单次 LLM 调用、检索和上下文示例
使用前权衡
  • Agentic systems 往往以更高延迟和成本换取更好任务表现。
  • Workflow 适合明确任务；agent 适合需要灵活决策的规模化问题。
  • 如果简单 LLM 调用已经足够，就不必构建 agent。
Frameworks工具选择不是架构替代品

框架能降低起步成本，也可能增加看不见的抽象层

可简化

调用 LLM、定义和解析工具、串联调用等低层任务更容易开始。

会遮蔽

额外抽象可能让底层 prompt 和 response 更难调试。

建议

优先直接使用 LLM API；如果使用框架，要理解底层代码。

Building blockAugmented LLM

增强型 LLM 是所有模式的基础构件

原文图示要点

增强型 LLM 不是单独模型调用，而是围绕检索、工具、记忆和清晰接口建立的能力组合。

模型主动使用能力

当前模型可以生成搜索查询、选择合适工具，并判断要保留哪些信息。

实现重点

根据具体用例定制能力，并为 LLM 提供简单、文档充分的接口。

Workflow map从可预测到开放式

五类常见 workflow 覆盖不同任务形态

Prompt chaining

把任务拆成连续步骤，每步处理上一步输出。

Routing

先分类，再分发给更专门的后续任务。

Parallelization

并行处理子任务，或用多视角提高置信度。

Orchestrator-workers

由 orchestrator 动态决定子任务和 worker 分工。

Evaluator-optimizer

生成结果，再用明确标准评价并迭代优化。

Agents

用于难以预先硬编码路径的开放式问题。

Fixed pathsPrompt chaining 与 routing

当任务能被清晰拆解或分类时，固定路径更可控

Prompt chaining
  • 适合能干净拆成固定子任务的场景。
  • 用延迟换取准确率，让每次 LLM 调用更容易。
  • 示例：先写大纲，再检查标准，最后生成文档。
Routing
  • 适合输入类别明确、不同类别需要不同处理策略的任务。
  • 通过分类实现关注点分离，避免一种 prompt 牺牲另一类输入表现。
  • 示例：把客户问题分到退款、技术支持或通用问答路径。
Adaptive workflows并行、编排、评估

更复杂的 workflow 应该对应更复杂的不确定性

Parallelization

当子任务可并行，或需要多种尝试和视角来提高置信度时使用。

Orchestrator-workers

当无法预先判断需要哪些子任务时，由 orchestrator 动态拆解和分配。

Evaluator-optimizer

当有清晰评价标准，且迭代改进能带来可衡量价值时使用。

Agents开放式问题的自主系统

Agents 适合无法预测步骤数、也无法硬编码路径的问题

使用前提

任务开放、步骤不确定，并且你能在一定程度上信任模型的决策过程。

风险边界

自主性会带来更高成本和复合错误风险，因此需要沙盒测试与护栏。

“Agents' autonomy makes them ideal for scaling tasks in trusted environments.”

Practice两个高价值应用域

客户支持与编码任务体现了 agent 的实际价值

Customer support

Support agents 能结合对话、工具和业务上下文处理多步骤问题，但必须控制权限和错误传播。

Coding agents

软件开发场景天然需要搜索、修改、测试和迭代，agent 能从补全扩展到自主问题解决。

Takeaway可发布系统的三条原则

从简单、透明、可验证的模式开始

从简单开始

优先单次 LLM 调用和清晰 workflow，复杂度必须由任务收益证明。

保持透明

理解框架底层行为，避免 prompt、response 和工具调用被抽象层遮蔽。

严格验证

对 agent 进行沙盒测试、加护栏，并针对开放式任务建立评价机制。
